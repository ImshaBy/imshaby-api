# Решение о миграции расписания на RRULE

Переносим по одной фиче. HTTP-адаптеры v1 и v2 вызывают общие прикладные сценарии. Домен независим от версии API, HTTP DTO, Spring MVC и Spring Data MongoDB. Адаптеры работают с хранилищем через прикладной слой. После отключения v1 её адаптер можно удалить. Прод переходит с v1 на v2 после подготовки backend.

Каждая имша хранит календарное описание с DTSTART и RRULE. Для разовой имши используем FREQ=DAILY и UNTIL, равный моменту DTSTART. Для второй пятницы месяца используем FREQ=MONTHLY;BYDAY=2FR. Конец серии задаёт включительный UNTIL, бессрочное правило верхней границы не имеет. Длительность отдельной имши сохраняется. Точечная отмена добавляет EXDATE с исходным временем начала, отмена серии помечает Mass удалённой. Календарь и поиск учитывают одинаковые правила.

При миграции сохраняем идентификаторы и наблюдаемый контракт v1, включая дни, время, исходные границы периода, ошибки и поведение изменения и удаления. До переключения клиента v1 создаёт разовые и еженедельные расписания.

Gradle build запускает проверку архитектурных зависимостей мигрированных фич и интеграционные тесты. Проверяем HTTP через Spring и реальную тестовую MongoDB. Unit-тесты используем для изолированных вычислений. Для первого сквозного сценария проверяем запись через v1, сохранённый RRULE и чтение прежнего ответа через v1.
