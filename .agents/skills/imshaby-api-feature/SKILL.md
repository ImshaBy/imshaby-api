# Фича API в imshaby-api

## Перед реализацией

- Изучить связанные маршруты, DTO, доменные модели, сервисы, запросы к хранилищу и существующие HTTP-тесты. Сохранить поведение старых маршрутов.
- Оценить защитное покрытие поведения, которое может измениться. Если его недостаточно, сначала добавить HTTP-тесты по принципам `api-v1-contract-tests`, затем реализовать фичу. При задаче только на покрытие старого контроллера использовать `api-v1-contract-tests` непосредственно.
- Зафиксировать контракт новой версии: маршрут, входные данные, форму ответа и существенные правила выборки. Не превращать правило одной фичи в общее правило для других.

## Версия и структура

- Размещать код в `by.imsha.feature.<сущность>.<операция>.vN`, например `by.imsha.feature.parish.inactive.map.v2`. Внутри выделять `controller`, `service`, `mapper` и другие пакеты, когда они нужны. Следовать этой группировке в OpenAPI-спецификации, тестовом Java-пакете и новых ресурсах тестов.
- Для новой версии использовать отдельный маршрут, спецификацию OpenAPI, сгенерированные типы и контрактные тесты. Сохранять поведение предыдущих версий. Имена Java-классов фичи оставлять без суффикса версии; версию изолирует пакет.
- Создать `FeatureMetadata` в пакете версии с константой `COMPONENT_VERSION`, например `"Version2"`. В аннотациях Spring задавать имя каждого компонента как его обычное имя с маленькой буквы плюс `COMPONENT_VERSION`. Не выносить целые имена компонентов в отдельную утилиту.
- Хранить OpenAPI-спецификацию в логичном пути фичи и подключать её к Gradle-генерации. Контроллер фичи наследует сгенерированный контроллер и только делегирует вызов сервису фичи. Логика выборки, локализации и сборки ответа принадлежит сервису; сервис обращается к другим сервисам, а не к репозиториям напрямую.
- Преобразование моделей выполнять через MapStruct. Для mapper использовать `componentModel = MappingConstants.ComponentModel.SPRING` и `implementationName`, составленный из имени mapper с маленькой буквы и `COMPONENT_VERSION`. Не регистрировать mapper вручную через `@Configuration`.
- Если нужен новый HTTP-клиент, генерировать Spring HTTP Interface. Существующие Feign-клиенты не менять без отдельного требования.

## HTTP-контрактные тесты

- Проверять HTTP через `MockMvc` с контекстом Spring и реальной MongoDB в Testcontainers. Контролировать внешние HTTP-зависимости заглушками; сбрасывать базу, кэши и заглушки между тестами и выполнять тесты с общим состоянием последовательно.
- Новые фикстуры размещать в `server/src/test/resources/feature/<сущность>/<операция>/vN/<имяТеста>/`. Каждый JSON-файл должен представлять настоящий запрос или ответ API. Для нескольких запросов или ответов использовать отдельные файлы. Не добавлять `mockmvc` в новые пути и не переименовывать старые ресурсы.
- Проверять статус, значимые заголовки, полную структуру и значения ответа, а также сохранённое состояние, когда это важно. Если порядок выдачи не определён контрактом, сравнивать точный набор элементов без зависимости от порядка. Не проверять внутренние имена Spring beans.
- Если добавление значения enum требует осознанного пересмотра поведения фичи, фиксировать текущий набор значений в контрактном тесте. Не ограничивать будущие значения в коде или OpenAPI только ради такого теста.

## Проверка

- Следовать локальному `AGENTS.md` при запуске Testcontainers. Не переносить настройки Windows VM, Docker-туннеля или ключей в код, тесты и общие конфигурационные файлы.
- Запустить тесты новой фичи и затронутых старых маршрутов. Проверить итоговый diff и сообщить, что фактически прошло, а что осталось непроверенным.
